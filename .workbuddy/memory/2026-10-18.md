## LLM Proxy Gateway（X 项目）透传完整性诊断

**结论：不是真正的字节级透传。** 请求走 `JSON body → Pydantic 模型 → model_dump() → 重新序列化` 链路（app/main.py 端点签名用 `ClaudeRequest` / `OpenAIRequest`），响应走 `resp.json() → return dict`。README 与 proxy.py docstring 声称的 "完全透传 / 所有字段原样传递" 与实现不符。

实测确认（脚本已跑完删除，非推断）：

请求体丢失：
- `app/models.py` 只有顶层请求模型有 `extra="allow"`，**嵌套模型全部没有** → `TextContent` / `ThinkingContent` / `ToolUseContent` / `ToolResultContent` / `ImageContent`、`Message`、`OpenAIMessage` 均丢弃未声明字段
- Claude `cache_control` 全丢（system / text / tool_use / tool_result 四处实测均丢）→ prompt caching 失效
- OpenAI assistant 消息的 `tool_calls`、`reasoning_content`、`name`，tool 消息的 `tool_call_id` 全丢 → 多轮 function calling 断裂
- `redacted_thinking`、`document`（PDF）、`server_tool_use` 等未声明 block 类型 → Pydantic 校验失败 → 下游 HTTP 422
- 默认值注入：`temperature=1.0`、`top_p=1.0`、`stream=false`、`max_tokens=1024` 即使下游未传也会补进上游 body（`exclude_none` 不排除默认值）

请求头全丢：proxy.py 里 headers 硬编码为 x-api-key / anthropic-version / content-type（或 Authorization），下游的 `anthropic-beta`（1M 上下文、interleaved thinking）、`OpenAI-Organization` 等一概不传。

响应侧：
- 非流式响应体完整（含 `cache_read_input_tokens`），但**响应头全丢**（`request-id`、`anthropic-ratelimit-*`）
- `resp.raise_for_status()` → 上游 400/429 → 下游收到 **500 Internal Server Error**，上游 error body 与 `retry-after` 全丢
- 流式：SSE 内容逐字节等价 ✅（实测 True）；但上游报错时下游已拿到 200 头 + 空 body，静默失败

日志也不可信：`log_request` 记录的就是裁剪后的 `req.model_dump()`，无法用它回溯丢了什么。

注：`model` 被主动替换为 `upstream_model`（设计意图，非 bug）。

## 改造：v2.0 字节级透传（已完成并验证）

按宝哥要求改为「Claude→Claude、OpenAI→OpenAI 完全透传，跨协议不再支持」。

**做法**：请求路径彻底摘掉 Pydantic 模型，端点签名改为 `request: Request` + `await request.body()`。
body 唯一改动是顶层 `model` 值，用 `rewrite_top_level_model()` 按字节扫描替换（UTF-8 多字节字符字节值均 ≥0x80，不会撞上 JSON 结构字符，因此按字节扫描安全）。

**关键文件**：

- `app/proxy.py`：`rewrite_top_level_model` / `build_upstream_headers`（透传业务头、只换鉴权头与 content-type）/ `filter_response_headers`（剔逐跳头与 content-encoding）/ `collect_sse_line`
- `app/models.py`：**已删除**
- `verify_passthrough.py`：新增，自带假上游（uvicorn 随机端口 + TestClient），29 项保真度断言，离线可跑
- `test_proxy.py`：#16 断言适配新的标准错误结构（error 为对象而非字符串）

**验证结果**：`verify_passthrough.py` 29/29；`test_proxy.py` 16/16（真实 DeepSeek 上游）。
上游 400 不再变 500，`retry-after`、`request-id`、限流头均可透出。

**已知遗留**（未改，非本次范围）：`ConversationLogger` 是「读整文件→append→写回」，高并发下存在读-改-写竞态会丢日志记录。

## 核查：「外部检测报告称改造后输出质量退化」

**结论：现象真实存在，但「由本次改造导致」不成立。** 未回退透传改造。

取证方式与证据：
1. 用 `git worktree` 检出 HEAD（旧版）与当前（新版），同一请求分别喂假上游，抓实际 body 做确定性 diff。差异仅 4 处：
   - 旧版多注入 `temperature:1.0`（下游未传时）、`top_p:1.0`、`stream:false`
   - 头 `anthropic-version` 从空字符串 → `2023-06-01`
   - 其中版本头实测无影响：直连上游各 5 次，输出/长度完全一致（completion 均值 24.6 vs 23.0）
2. 旧版日志（`logs/...10-18.json` 12:17-12:22 段）显示**旧版同样在 reasoning**：`1+1` 请求 reasoning_tokens=12、text='2'。思考从未被代理控制。
3. 同一 prompt、同参数（T=0, mt=2000）相邻两次调用，thinking 从 28 tokens 跳到 1063 tokens；整批 T=0 样本 thinking 长度 37~6033 字符，跨度 163 倍 → 上游非确定性。
4. **thinking 长度与「是否只输出数字」无相关**：thinklen=2708 那次严格输出 `5021`，thinklen=2655 那次输出「因此，答案是**5021**」。
5. 延迟与 thinking 字符数相关系数 **r=0.861**（40 条样本，1.56s→9.22s）→ 延迟是思考长度的函数，不是代理开销。新版还去掉了 `resp.json()` 往返，理论上更快。
6. 两版对比不是同一实验条件：旧版 15 条样本全部 T=1.0（下游未传、被代理注入），新版 20 条全部 T=0（下游显式传）。检测脚本本身改过。
7. T=0 合规 7/22（32%），T 未传 7/15（47%）→ temperature=0 对 reasoning 模型反而不利，印证报告「T=0 也无法抑制」。

**唯一真实保留的行为差异**：下游不传 `max_tokens` 时，旧版强制 1024、新版不传（用上游默认）。本次检测样本都显式传了 max_tokens，故不适用；但如果要复现旧的确定性，可在 `model_config.yaml` 加显式默认参数配置，而不是回退到 Pydantic 隐式注入。

宝哥确认：**默认注入 temperature/top_p 本来就不对，不改它**（即不做隐式默认参数注入）。

## 日志重构：JSONL 追加写（已完成并验证）

**动机**：原实现每写一条日志都「读整个 JSON 数组 → append → 整体重写」，并发下是读-改-写竞态，进程中断会写坏整个文件。

**新方案**：
- 路径 `logs/{YYYY-MM-DD}/conversations_{客户端}_{下游模型}_{上游模型}.jsonl`（日期本地时区，客户端取 IP）
- 一条对话一行，`request` + `response` 同条记录；不再要求整文件是合法 JSON
- 写入 = `O_APPEND` 打开 + 单次 `os.write` + **跨进程文件锁**（Windows `msvcrt.locking` / POSIX `flock`）+ 进程内 `threading.Lock`
- 本地拒绝（400：非法 JSON / 跨协议 / 未知模型）与上游不可达（502）也记录
- 时间戳改为带本地时区 ISO 8601

**关键实测（值得记住的坑）**：**仅靠 `O_APPEND` + 单次 write 在 Windows 上不足以保证跨进程原子追加**——4 进程写 600 条实测丢 126 条。原因是 Windows CRT 的 `_O_APPEND` 是「seek 到末尾再写」，存在竞态。加 `msvcrt.locking` 后 600 条零丢失。

**验证**：`verify_logging.py` 12/12（多线程 500 条、多进程 4×150、端到端按客户端+模型分文件、跨协议拒绝留痕）；`verify_passthrough.py` 29/29；`test_proxy.py` 1-4 真实上游通过，流式 events 84/75 条正常采集。

**注意**：验证脚本会把 TestClient 流量写进真实 logs/，已在 `verify_passthrough.py` 里把 `conversation_logger._root` 指向临时目录（atexit 清理）；`verify_logging.py` 同理。

## 新增访问鉴权（已完成并验证）

**需求**：非本地客户端必须带正确 key；本地（localhost / 127.x.x.x）不校验；key 在 yaml 配置；考虑兼容。

**实现**：
- 新增 `app/auth.py`：`is_loopback()`（localhost、127/8、::1、IPv4-mapped ::ffff:127.x）、`extract_token()`（Bearer / x-api-key / 裸 Authorization）、`secrets.compare_digest` 常量时间比较
- `app/config.py` 解析 `auth` 段：`keys` 支持 list（记为 key1/key2）与 dict（名字进日志）；**`enabled` 省略时按 keys 是否为空推断**——填了 key 就自动启用
- `app/main.py` 加 HTTP 中间件统一鉴权；`/health` 放行，其余（含 `/v1/models`、`/docs`）都过
- 401 按下游协议返回标准错误结构；对话端点留痕但**不落请求体**
- 日志新增 `auth` 字段 `{"mode": local|key|disabled|denied, "principal": key名}`，不记 key 明文
- `enabled: true` 但 keys 为空 → **fail closed**（非本地全 401）+ 启动 warning

**关键设计**：下游用于鉴权的 `Authorization`/`x-api-key` 不会被转发给上游（转发层本来就会用上游凭证覆盖），不冲突。

**验证**：`verify_auth.py` 27/27；回归 `verify_passthrough.py` 29/29、`verify_logging.py` 12/12、`test_proxy.py` 16/16（真实上游）。

**注意**：`verify_passthrough.py` / `verify_logging.py` 已显式把 `_auth` 置为 disabled，避免以后开启鉴权导致离线验证脚本失败。

**配置写法确认**（宝哥质疑 yaml 注释与回复示例不一致）：实测 `keys: ["sk-a","sk-b"]`（流式）与 `keys:` + `- "sk-a"`（块状）解析结果完全相同，映射写法同理，**两种都准确**。已清理 `model_config.yaml` 里冗余的 `# keys: []` 行（与下方实值重复、易误解），注释与 README 统一为块状写法。另实测：值不加引号时纯数字会被 YAML 解析成 int（代码里 `str(value)` 已兜住），流式列表漏闭合会直接 `ParserError` 导致服务起不来——故注释强调值一律加引号。

**踩坑提醒**：在 Git Bash 里用 `python -c "...\n..."` 传含 `\n` 的字符串会被 MSYS 路径转换改写成 `/n`，导致 YAML 解析出诡异结果。验证这类内容要写成脚本文件跑，不要用 `-c`。

## QA 复核（独立对抗测试）发现的 4 个缺口及修复

**教训：自写验收脚本有盲区。** 首轮 `verify_hardening.py` 28 项全过，但独立构造攻击场景后仍有 4 处不达标：

1. **鉴权失败不受限流约束**（最严重）：限流判断写在 `authenticate()` 之后，401 直接 return，不计入配额。实测限流 3/min 下连续 30 次错 key 全部 401、零 429，每次还写一行日志 → 可爆破 key + 日志放大。
   - 修复：**限流判断移到鉴权之前**，401 同样消耗配额。复验 `{401: 3, 429: 27}`。
2. **响应体未做日志截断**：`max_logged_body_mb=1` 时 5MB 上游响应仍被完整写入（+5.00 MB）。只截断了 request，漏了 response。
   - 修复：非流式按 `len(body)`、流式按累计字节判断，超限只记 `{"__truncated__": true, "bytes": N}`。复验 +0.00 MB。
3. **空 `anthropic-version` 覆盖配置值**：下游传空串，上游收到 `''` 而非配置的 `2023-06-01`。
   - 修复：白名单透传时跳过空值/纯空白头值。
4. **`x-internal-*` / `server` 仍回传**；另 `max_body_mb=0` 语义与 `rate_limit_per_minute` 不一致。
   - 修复：响应头前缀加 `x-internal-`、剔除 `server`；`max_body_mb=0` 统一为不限。

**复验**：上述 4 项已固化进 `verify_hardening.py`（第 10-13 节），现 **33/33**；回归 29/29、27/27、12/12、16/16 全通过。

**剩余风险（未处理，需产品决策）**：
- 响应头仍是**黑名单**（请求头已白名单），未知自定义头理论上仍会透传
- 限流是进程内计数，`--workers N` 时实际阈值 ≈ N × 配置值
- 本地回环免 key 是设计选择：同机其他进程/容器访问 127.0.0.1 可绕过鉴权
- `/health` 不限流；日志含完整对话内容（PII），依赖文件权限保护

## 新增 OpenAI Responses API 支持

**背景**：宝哥问是否支持 `/v1/responses`，实测原实现直接 404（只注册了 messages / chat 两个路由）。

**DeepSeek 实测（关键事实，以后不用再查）**：
- `POST /v1/responses` 与 `/responses` **都可用**（200），选用 `/v1/responses` 与现有风格一致
- 模型名 `deepseek-v4-flash` 和文档写的 `deepseek-flash` **都接受**
- 请求：`input`（string 或 item 列表）/ `instructions` / `reasoning.effort`（none|low|high|max）/ `max_output_tokens` / `text.format` / `tools` / `store` / `previous_response_id`
- 响应：`object=response`，`output[]` 含 `message`/`reasoning`/`function_call`，内容块 `output_text` / `reasoning_text`
- 流式标准 SSE：`response.created` → `response.output_item.added` → `response.reasoning_text.delta` / `response.output_text.delta` → `response.completed`
- **API 是无状态的**，多轮要客户端回传完整 `input`

**实现**：`proxy.py` 的 `_ENDPOINT_PATH` 从「协议格式→路径」改为「**端点类型**→路径」（messages/chat/responses）；`_handle(request, downstream_format, endpoint)` 加第三个参数，`downstream_format` 仍只管 base_url 与鉴权头。新增路由 + `_CONVERSATION_PATHS` 加路径即可，鉴权/限流/日志自动覆盖，流式复用现有 SSE 逐字节转发。

**验证**：`test_proxy.py` 新增 #17 真实上游用例 → **17/17**；`verify_passthrough.py` 新增 6 项 Responses 断言 → **35/35**；回归 hardening 33/33、auth 27/27、logging 12/12。

**注意**：代理支持 ≠ 上游支持。其他厂商若只有 chat completions 兼容层，打 `/v1/responses` 会原样收到上游 404/400。

## 追加：model_config.yaml 是否需要跟着改（结论 + 顺带修一个 bug）

**结论：不需要改。** `build_upstream_url()` 用 `base_url.openai` 拼 `/v1/responses`，DeepSeek 的 chat 与 responses 共用 `https://api.deepseek.com`。实测 13 个模型拼接结果全部正确（`https://api.deepseek.com/v1/responses`、`https://api.openai.com/v1/responses`、`.../compatible-mode/v1/responses`、`http://192.168.31.20:8000/v1/responses`）。
**配置约束**：base_url **不要带 `/v1`**，否则会拼成 `/v1/v1/...`（已在 README 注明，现有 6 个 base_url 都符合）。

**顺带发现并修复的 bug：legacy 格式绕过跨协议校验。**
`base_url` 用字符串 + `provider` 字段的旧写法，在 `get_upstream_info()` 的 legacy 分支**没有校验 `downstream_format`**，直接返回配置的 provider。实测：
- `qwen3.6-plus-anthropic`（provider=anthropic）打 `/v1/responses` → 用 `Authorization: Bearer` 打 Anthropic 端点
- `Qwen3.6-Coder`（provider=openai）打 `/v1/messages` → 用 `x-api-key` 打 OpenAI 端点

两者都会让下游只看到上游 401，违反"跨协议一律 400"的决策。已在 `config.py` 的 legacy 分支补 `provider != downstream_format` 拒绝。

**复验**：`verify_passthrough.py` 新增 2 项 legacy 用例 → **37/37**；`test_proxy.py` 17/17；hardening 33/33、auth 27/27、logging 12/12。
